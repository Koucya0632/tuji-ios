# 例句的斷詞與釋義是撰寫好的資料，不是裝置上算出來的

例句與**譯義**裡的實詞與片語可以點，點下去說這個詞**在這句話裡**是什麼意思。切分、原形、
詞性、釋義是**撰寫好並簽進版控的內容**（`tuji-web/data/example-spans.json`，由
`scripts/load-example-spans.ts` 載進 `sentence_spans`），隨 word detail 的 payload 送到
App。App 收到切分結果把它畫出來，**不持有字典，也不跑斷詞**。

儲存以**句子本身**為鍵，不是以某一列為鍵：標註是那個字串的性質，所以例句與譯義共用一張表，
同一句話標一次到處都通。句子被改寫時舊標註自然對不上，於是退回純文字——**沒有比標錯好**。

執行期沒有任何一層會呼叫模型：不是請求時、不是建置時、也不是 enrich 時。跟
`data/etymology-en.json` 同一條路——幾百句的封閉語料值得寫一次、擁有它，並且在 diff 裡讀得到。

## 為什麼不用 iOS 內建的 NLTagger

`NLTagger` 就在系統裡，免費、離線、支援英日雙語，`running → run` 一行就拿得到。它是任何人
接手這件事時的第一直覺，所以要說清楚它為什麼不夠。

它給的是**原形**，不是**意思**。拿到 `run` 之後還要拿它去查一本字典——而這個專案沒有那本
字典。Tuji 的字典是策展式圖鑑：每個 direction 約 480 個詞頭，每一個都有圖片、分類、CEFR
等級，是被挑進來教的。`quickly`、`under`、`carefully` 永遠不會有詞條，因為它們永遠不會有
圖片。裝置端斷詞的終點是一把查不到東西的鑰匙。

第二件它給不了的是**片語邊界**。`look forward to` 對任何斷詞器都是三個 token，對學習者是
一個單位，而把中間那個 `to` 單獨翻成「到」是錯的——不是沒用，是錯的。片語邊界要看得懂整句
才判得出來。

## 為什麼是撰寫的資料，而不是跑一次模型

[ADR-0006](0006-furigana-segmentation.md) 的結論是模型不能當日文讀音的權威，並且引用了
`lib/ja-reading-overrides.ts` 與 2026-08 的那次修復。同一條教訓在這裡的答案是：不要把它交給
模型。2,327 句是一個人讀得完、改得動、在 code review 裡看得見的量，而一次性產出的東西如果
只存在資料庫裡，下次想修一個詞就只能重跑整批。

**可驗的部分照樣驗。** 標註是**全覆蓋**的：每一個字元都落在某一塊裡，串起來必須一字不差地
重寫出原句。這跟 `reading_segments` 用的是同一條不變量。載入腳本在寫入前比對，任何一句不符
就整批拒絕寫入；伺服器在送出前再比一次；App 在解碼時第三次比對，不符就整句退回純文字。

**不可驗的部分不承重。** 釋義本身沒有辦法用算術檢查。差別在讀音會進到拼字關卡變成考題，錯的
讀音會教錯人；釋義不會——它不進 SRS、不出題、不影響任何一次複習排程，它是讀句子時的一個輔助。
一個偏了的釋義的代價是這一次讀得不夠準，不是把錯的東西練進長期記憶。而因為它是版控裡的一個
JSON，修一個詞就是改一行、跑一次載入腳本。

## 為什麼是全覆蓋的塊，不是字元位移

位移看起來更省，但它要求兩種語言對「一個字元是什麼」有共識。JS 天生數 UTF-16 code unit，
Swift 的 `Character` 是 grapheme cluster，Postgres 的 `substring` 數 code point；三者在
組合字與 emoji 上會分家。全覆蓋把這個契約整個消掉：伺服器送出一串塊，App 逐塊接起來組成
`AttributedString`，**從不對字串做索引**。而不變量退化成一次字串比較。

這也讓「可不可點」不需要自己的欄位：有釋義就可點，虛詞與標點就是沒有釋義。

## Consequences

- **標註有版本。** `sentence_spans.version` 比照 `ATLAS_ENRICH_VERSION`：格式改了就升
  `SPANS_VERSION`，載入腳本重寫、讀取端忽略落後的列，所以升級永遠不會在畫面上只做一半。
- **對不上就當作沒有，不是錯誤。** 一句話的塊串不回原句時，App 畫的是今天的純文字例句。
  這是這個功能唯一的失敗模式，而它剛好等於功能上線前的樣子。
- **詞塊不連回你正在看的那一頁。** 兩種句子都會提到自己的詞頭，而且是刻意的——例句存在就是
  為了示範那個詞，譯義開頭就是「X」是…。所以最好點的那一塊，剛好是「看完整詳情」會把當前
  頁面再推一次的那一塊。這不是邊角情況：1,303 個例句詞塊與 493 個譯義詞塊都指向自己。規則
  放伺服器（`unlinkSelfReference`）而不是卡片裡，因為卡片掛在畫面層級、永遠不知道句子來自
  哪個詞；**該塊仍然可點，只是少了那顆按鈕**。
- **釋義要存三份（zh-Hant / ja / en），zh-Hans 由 OpenCC 導出。** 缺該語言時退回 zh-Hant，
  跟 `lib/word-localize.ts` 對承重欄位的規則一致——**可點與否必須跟介面語言無關**，否則同
  一句話在日文介面會少掉一半可以點的字。
- **自製圖鑑不在範圍內。** 那些詞根本沒有例句：`lib/atlas/enrich.ts` 把 `examples` 寫死成
  `null`。`atlas_items.example_target` / `example_zh_hant` 有被讀出、有隨 `/api/atlas/sync`
  送到 iOS、iOS 也解了出來，但沒有任何地方寫入或渲染——是死欄位，不是這個功能的接口。
- **語料是封閉的，所以這是一次性的成本。** 實際是 **2,327 句、21,208 個詞塊**——例句 1,373
  句（英 687 / 日 686）加譯義 954 句（477 個詞頭 × 英日），一次寫完。沒有使用者能產生新句子；
  新增目錄詞時，載入腳本會把沒有標註的句子列出來，那份清單就是待辦。
