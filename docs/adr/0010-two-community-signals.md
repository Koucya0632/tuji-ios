# 社群的兩條訊號通道是兩條，不是一條沒收乾淨的

`CommunityFeedRefresh` 與 `CollectionBookmarkStore` 都是 app root 的
`@Observable`，都在說「一次社群變更被確認了」，而 `AtlasPublicFeedView` 在相隔
三行的地方各讀一條——一條用 `consume()`，一條用 `.onChange(of: revision)`。

看起來像同一件事被做了兩次。它不是。這份 ADR 存在是為了讓下一次架構檢視不必
把這個結論重新推導一遍。

## 兩者實際上的差別

|  | `CommunityFeedRefresh` | `CollectionBookmarkStore` |
|---|---|---|
| 載荷 | 一個 bit | 一個值：哪個合集、收了沒 |
| 消費 | 載入時**消費一次** | 掛載中**反應式套用** |
| 消費者做什麼 | 決定要不要繞過 URLCache 重抓 | 直接把那一列改掉，**不重抓** |
| 漏掉的代價 | 列表暫時是舊的 | 那一列的收藏狀態是錯的 |
| 必須撐過 | 從別的畫面發布，到 feed 下次出現——可能很久，也可能永遠不會 | 只需要送到現在掛著的畫面 |

`revision` 這個計數器不是 `lastChange` 的補丁。它存在是因為**重複的同一個變更
必須再觸發一次**：連續收藏、取消、再收藏同一個合集，`lastChange` 兩次相等，而
兩次都要套用。

`consume()` 的一次性也不是省事。它存在是因為那個訊號**要活過畫面的生滅**：發布
的當下 feed 可能根本沒被掛起來。

## 為什麼合併不會 concentrate

把兩者收成一條，消費規則只能二選一：

- **都改成消費一次。** 沒掛著的畫面收不到收藏變更，而掛著兩次的畫面沒辦法套用
  兩次。這是把一個現在正確的行為弄壞。
- **都改成觀察計數器。** feed 就得自己記住「第 N 號我處理過了」並跨畫面出現保存
  它——那是**更多**狀態，不是更少。

兩個方向都把複雜度從通道推到消費者身上。套 deletion test：刪掉其中一條不會讓複
雜度集中，只會讓它搬家——而跨畫面的訊號總得住在某處。

## Consequences

- **兩條通道各自保留自己的消費協定。** 三行之隔用兩種寫法看起來刺眼，但那兩種
  寫法回答的是兩個不同的問題。
- **它們跟 `AtlasMutationRefresh` 是不同的東西。** 那個 module 回答的是「一次
  authoring 側的變更要讓什麼失效」，是一套政策；這兩條是傳輸，不是政策。
- **如果哪天出現第三條**，先問它是「撐過畫面生滅的一次性旗標」還是「送給掛著的
  畫面的廣播」，再決定它跟哪一條同族。這兩類本身是穩定的分類。
