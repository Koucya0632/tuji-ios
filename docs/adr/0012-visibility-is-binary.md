# 可見性是二值的：私有，或公開

`user_atlas_items.visibility` 有三個值。`'friends'` 是其中一個，`user_friendships`
與 `atlas_item_grants`（逐項 `scope='view'` 授權）兩張表都真的存在，
`listAtlasFriendVisibleItems` 會查它們，`/api/atlas/friends` 與 web 的
`/atlas/friends`（「朋友圖鑑」）會渲染結果。

看起來像一條做到一半的功能。它比那更明確：**那兩張表在整份應用程式碼裡沒有任何一個
INSERT，也沒有任何一行把 `visibility` 寫成 `'friends'`。** 沒有寫入端，所以那個頁面
對每一個使用者、在任何時候都保證是空的——不是「還沒有人用」，是**不可能有東西**。

這份 ADR 存在，是因為資料表會留在資料庫裡（`migrate.ts` 是 append-only），所以下一個
讀到 `visibility = 'friends'` 的人一定會問「這是不是還沒接完」，而答案不寫下來就只能
再推導一次。

## 決定

分享只有一種形狀：**通過審核閘門，對所有人公開。** 中間沒有第三種可見性。

讀路徑移除（頁面、路由、查詢函式、那個連結）；資料表留著不動。

## 為什麼不是三值

**審核閘門是公開側唯一的一條界線。** 這條界線在程式碼裡是實體的：
`Atlas.swift` 的檔頭寫著「crossing from one file to the other is exactly the
moderation gate」——一個型別在哪個檔案裡，就回答了「這是私人的還是大家的」。

第三種可見性會在那條界線上開一個洞：好友看到的照片**沒有經過任何審核**。而審核閘門
不是裝飾，它擋的是別人上傳到我們儲存空間、再由我們的 CDN 送出去的圖片。一旦有一條
繞過它的路，「Tuji 上看得到的東西都審過」這句話就不再為真，而那句話目前是整個公開側
的前提。

其次，三值會讓已經定下來的每一條規則都多一個分支要回答：好友看到的能不能收進圖鑑
（那會不會產生沒有 `atlas_public_items` 的 `atlas_saves`）、作者刪除時算不算跨帳號
損害、封鎖對它有沒有效、檢舉的目標是什麼。這些都不是不能答，而是**一條真功能的量**，
不是一個欄位值。

## 考慮過的替代方案

- **接完它。** 那是一條新功能，要有加好友、邀請、授權撤銷、以及上面那串規則的答案。
  沒有人在要求它，而它現在的成本是一個保證空白的頁面。
- **原封不動留著。** 最便宜，但下一個改公開邏輯的人會在 grep 裡撞到一條**跑得動的、
  繞過審核閘門的查詢**，然後花時間確認它是不是真的沒有人走。這正是這份文件要省掉的
  那次確認。

## Consequences

- **`CONTEXT.md` 現在說「可見性是二值」，而程式碼不再有第三種的讀路徑。**
- **資料表留著。** migration 是 append-only，而刪表換不到任何東西。它們現在是純粹的
  歷史，這份 ADR 是它們的說明。
- **如果哪天真的要做好友分享**，起點是這份文件的「為什麼不是三值」那一節：先回答
  審核閘門怎麼辦，再談資料表。
