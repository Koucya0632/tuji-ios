# 用量紀錄在刪帳號後保留，只切斷身分

用量紀錄（tuji-web `assistant_usage`）是所有付費 AI 功能——助手四項與拍照做卡——的成本與
扣點，用途是算**實際倍率**、判斷定價對不對。用戶刪除帳號時，他的列**不刪**：外鍵改為
`ON DELETE SET NULL (user_id)`，列留著，`user_id` 變成 null。旁邊的點數表、識別操作表全都
跟著帳號 CASCADE 刪掉，只有這張不會。

**為什麼**：最可能刪帳號的，是開小號試用、或用得很兇之後離開的人——正好是拉低實際倍率的
那群。跟著刪，倍率的歷史會隨時間越變越好看，全站成本也對不上供應商帳單。這張表本來就只存
數字（功能、token、估算成本、扣點、價目版本、時間），不存問了什麼、答了什麼；切斷 `user_id`
之後已經不是個人資料，而定價只需要「哪個功能、哪個版本」，不需要「誰」。

## Considered Options

**跟著帳號刪（原本的 CASCADE）** — 被拒。最單純，但代價就是上面的偏差，而且是靜默的：沒有
任何數字會告訴你哪些列不見了。

**保留，`user_id` 換成不可逆雜湊** — 被拒。定價用不到「同一個人」這個維度；雜湊只會留下一條
看起來匿名、其實能把同一人所有列串起來的線。

**拍照做卡在刪帳號時才把成本複製出來** — 被拒。這樣用量表只有「已刪帳號」的拍照成本，在世
帳號的還在 `ai_operation_attempts`，看全部就得 UNION 兩個口徑不同的來源。改為在每次結算時
就寫一列（一次識別操作一列、重試加總、淨扣點），刪帳號時跟助手的列一樣切斷身分；識別操作表
本身的身分與 CASCADE 不動，它牽著點數預留與退款的狀態機。

## Consequences

**刪掉的列救不回來，留下的列也串不回人。** 改回 CASCADE 很容易，但這段期間保留的匿名列不會
因此消失，要另外清。

**隱私權政策要說一句。** 「刪除帳號後，不含身分的用量統計會保留」——App 內政策頁與商店頁
的隱私權標籤需要一致；本 ADR 落地時尚未改。
